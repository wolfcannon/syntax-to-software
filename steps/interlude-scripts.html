Notebooks to scripts

The second change of environment. The notebook got you an answer; this gets you something that can produce that answer again tomorrow, on another machine, without you in the room.

Why here, and not earlier

The same argument as the first level-up. A virtual environment solves a problem you have to have had, and until Unit 3 you had installed nothing. Now you have pandas, matplotlib, scipy and requests in the mix, an API key in your shell, and a notebook that quietly depends on all of it.

Three questions you cannot currently answer, and all three are about to matter:

  • Which versions of those packages does your analysis actually need?
  • If someone clones this repo, what do they run?
  • If the answer changes, was it your code or was it a package that updated underneath you?

Virtual environments

A virtual environment is a directory containing its own Python and its own installed packages. Activating it changes what python and pip mean in that shell, and nothing else on the machine is touched.

python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install pandas requests matplotlib scipy jupyter
pip freeze > requirements.txt

This is why .venv/ is in the repo's .gitignore and requirements.txt is not. The directory is a few hundred megabytes of rebuildable artefact; the file is the twelve lines that describe it.

The one that catches everyone

Jupyter runs whichever Python started it — not whichever one your shell has activated. Start jupyter lab from inside the activated environment, and if a notebook can't find a package you know you installed, run import sys; print(sys.executable) in a cell. It will be pointing somewhere you didn't expect, and that is the whole diagnosis.

The test of the split is whether clean.py can be imported and used with no network and no API key. If it can't, something that fetches has leaked into something that parses.

Running it from a terminal

python run.py                # the whole pipeline, raw data to figures
python -m bikewalk.clean     # one module, if it has a __main__ block

Each module ends with the guard you met in step 13:

if __name__ == "__main__":
    main()

Imported, __name__ is the module's name and the block is skipped. Run directly, __name__ is "__main__" and it fires. That one line is what lets a file be both a library and a command.

Exercises

The level-up: make it run without you

  1. Create and activate .venv, install what you need, and write requirements.txt.
  2. Split your module into fetch.py, clean.py and analyze.py, and add run.py that executes the pipeline end to end from raw data to saved figures.
  3. Make run.py print the numbers that matter as it goes: rows in, rows joined, coverage, rows dropped and why. A pipeline that prints nothing is a pipeline you cannot debug.
  4. Move the API key out of every file and into os.environ. Then grep your own repo for it and confirm it is gone.

Then the real test, and don't skip it: delete .venv entirely, recreate it from requirements.txt, and run python run.py. If it works, you have a project. If it doesn't, you have just found out what your analysis secretly depended on — which is exactly what the next unit is for.

You deleted the environment and rebuilt it — what usually breaks, and what does that tell you?

Four things, in rough order of how often they happen:

  • A package you never installed deliberately. It came in as someone else's dependency and you imported it anyway. pip freeze caught it; a hand-written requirements list would not have.
  • A file that isn't in the repo. A CSV sitting in your Downloads folder, referenced by absolute path. The fix is data/raw/ and a documented fetch step.
  • An environment variable. Your API key is in your shell profile, not in the project — correct, and worth stating in the README rather than discovering.
  • Import order. The notebook defined something before it was used because of the order you ran cells in, and run.py is stricter.

Every one of those is the same failure as the deleted-cell trap from the first level-up, one level up the stack: something worked because of state that isn't written down. Unit 4 is largely about removing the remaining places that can hide.
