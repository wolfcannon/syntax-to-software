Methods and strings

  • Values can do things to themselves. That is what a dot means.
  • Text can be cut apart by position.
  • Numbers can be printed the way a person would write them.

Dot notation

In step 2 you met five primitive types. One thing every type has in common is the ability to carry methods: things a value of that type knows how to do. Methods are accessed with a dot.

  • valuewhat you are asking
  • dotjoins the value to the method
  • methodwhat to do to it
  • argumentswhat it needs in order to do it

Almost every method hands something back. That is the call's return value, and the call becomes it — in the same way that 2 + 2 is 4, the call above is 'bikeable'. A method call is an expression, as step 1 uses the word.

And because the return value is itself a value, you can ask it to do something too. Each call works on what the one before it handed back:

"  Walk Score  ".strip()           # 'Walk Score'
"  Walk Score  ".strip().lower()   # 'walk score'

The value itself is never changed. Text is immutable in Python: name.upper() hands back a new piece of text and leaves name exactly as it was. Writing name.strip() on a line of its own therefore does nothing useful — you have to keep what it hands back.

Tip 💡: read it left to right

A method call is a sentence in that order: take this value, do this to it, using these — and hand back the result.

The parentheses surrounding the argument list are not decoration. The method name says which code to run; the parentheses are what tell Python to run it. They are there even when the argument list is empty:

"walkable".upper()   # 'WALKABLE'
"WALKABLE".lower()   # 'walkable'

Argument

A value handed to a method so it can do its work. Arguments go inside the parentheses, separated by commas.

How many a method needs depends on how much it cannot work out for itself:

"walkable".upper()                   # 'WALKABLE'   needs nothing — the value is enough
"walkable".count("a")                # 2            needs to know what to count
"walkable".replace("walk", "bike")   # 'bikeable'   needs what to replace, and what with

Where a method takes more than one, their order is what says which is which. Swap them and you have asked a different question — one that here quietly does nothing at all:

"walkable".replace("bike", "walk")   # 'walkable'   there is no "bike" in it to replace

Give a method the wrong number of arguments and it says so immediately:

"walkable".upper("x")
TypeError: str.upper() takes no arguments (1 given)

Leaving the parentheses off

"walkable".upper     # <built-in method upper of str object>
"walkable".upper()   # 'WALKABLE'

Without parentheses Python will return the method itself rather than executing the code defined in the method. It does this without complaint. If a value prints as something about a "method", this is what happened.

Which methods exist

They belong to the type, not to the value. Every piece of text has the same set; a number has a different set.

"18".upper()    # '18'
(18).upper()    # AttributeError: 'int' object has no attribute 'upper'

That error is worth recognising early. It rarely means you typed the name wrong. It usually means the value is not the type you thought it was, which is step 2's trap wearing a different coat.

Two shapes that do similar jobs

len("18") is a function, handed a value. "18".upper() is a method, belonging to one. Both take an input and give something back; they differ in whether the value goes before the dot or inside the parentheses.

There is no rule to derive here. len is a function and upper is a method because that is how Python is arranged. You learn them as you meet them.

Putting values into text

Sooner or later you have some values and you want a piece of text with those values in it — a label, a line of output, an identifier built from its parts.

The direct way is to join pieces together with +:

name = "Meridian-Kessler"
score = 14.5

"Walkability of " + name + " is " + str(score)
# 'Walkability of Meridian-Kessler is 14.5'

That works, and it is unpleasant. You are counting quotes and spaces, the sentence is broken into five pieces, and every value that is not already text needs str() around it. Forget one and you get:

TypeError: can only concatenate str (not "float") to str

String interpolation

Writing out the text you want, with gaps in it, and letting values fill the gaps when the line runs. The template stays readable because it is the shape of the answer.

f-string

Python's way of doing that. An f before the opening quote, and an expression inside each pair of braces.

f"Walkability of {name} is {score}"
# 'Walkability of Meridian-Kessler is 14.5'

Three things come free. The line now looks like what it produces, so you can check it by reading it. Values are converted for you, so str() disappears. And anything can go in the braces, because what is in there is an expression:

f"{bike} of {workers} cycle"
f"{bike / workers}"
f"{name.upper()}"

After a colon comes a format spec, which controls how the value is written out rather than what it is.

  • fmarks the text as a template, so braces mean something
  • expressionworked out first, then written into the text
  • :separates the value from how to write it
  • format spechow to write it — decimals, percent, padding, separators

The expression is worked out before anything is formatted, so a spec never has to care what it was given. The ones you will use constantly:

share = 0.01612
f"{share:.1%}"        # '1.6%'    percent, one decimal
f"{share:.4f}"        # '0.0161'  fixed decimals
f"{1303:,}"           # '1,303'   thousands separators
f"{14.5:>6.1f}"       # '  14.5'  right-aligned in 6 columns
f"{'3101.03':<10}|"   # '3101.03   |'  left-aligned, for tables

The debugging one

f"{workers=}" prints workers=1303 — name and value together. It is the fastest print-debugging tool in the language and you will use it in step 12 more than you expect.

Indexing and slicing

A string is a sequence of characters, indexed from zero. A slice s[a:b] takes from a up to but not including b, so the length of the slice is always b - a. That half-open convention is the same one that makes range and array slicing behave, and it is worth accepting early rather than fighting.

geoid = "180973401103"
geoid[0:2]    # '18'      state
geoid[2:5]    # '097'     county
geoid[5:11]   # '340110'  tract
geoid[11:]    # '3'       block group
geoid[-1]     # '3'       negative indices count from the end

Take it further

In an editor above, build the 12-character GEOID for every row of acs_raw and for every row of walk_raw, and print them side by side. They will not line up — acs_raw[3] and walk_raw[3] are different block groups entirely. Notice that now; step 8 is about fixing it properly.

Then print one formatted summary line per row: GEOID, walkability to one decimal, and bike share as a percentage.

Build a GEOID where the state arrives as the integer 1 and confirm it comes out as 01…

f"{1:0>2}" gives '01', and so does str(1).zfill(2). Both work; the f-string version reads better inside a larger template.

What you cannot do is str(state).zfill(2) where state came from int(geoid[:2]) of a GEOID you already damaged — padding restores the width but not the information. If a GEOID has already been through int(), you cannot always tell whether 1073 was Alabama county 073 or state 10 county 73. The zero has to survive from the source.

This is why step 10 turns build_geoid into a function and step 20 makes it the very first thing tested.

Tip 💡: look it up rather than guessing

Text carries 47 methods, and the table above is the handful this project needs. Nobody knows the rest from memory either. The list is written down:

  • docs.python.org — string methods, the whole set with what each one does.
  • help(str.zfill), typed into Python, which prints the same description without leaving what you are doing.

Knowing that a method probably exists, and where to check, is worth more than remembering its name.
