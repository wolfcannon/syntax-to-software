Keywords, types, and syntax

The small fixed vocabulary Python reserves for itself, the rule that indentation is grammar, and how to read the error you get when you break it.

A very small reserved vocabulary

Python has about 35 words you cannot use as names, and that is the whole of the language's fixed vocabulary. Everything else — print, len, int — is an ordinary name that happens to come pre-assigned.

import keyword
print(len(keyword.kwlist))   # 35
print(keyword.kwlist[:8])    # ['False', 'None', 'True', 'and', 'as', 'assert', 'async', 'await']

The practical consequence is a rule of thumb: if a name turns red in your editor and assigning to it is a SyntaxError, it is a keyword. If assigning to it works but something later breaks mysteriously, you have shadowed a builtin — list = [1, 2] is legal and then list(...) stops working for the rest of the kernel's life.

Indentation is syntax

In most languages layout is a courtesy to the reader. In Python it is the grammar itself: a colon opens a block, and the indented lines under it are the block. There is no closing brace, which means a misplaced indent is not a style problem, it is a different program.

total = 0
for row in rows:
    total = total + 1
    print(total)      # inside the loop — prints once per row

total = 0
for row in rows:
    total = total + 1
print(total)          # outside the loop — prints once, at the end

Both are valid. Only one is what you meant. Pick four spaces and never think about it again.

Expressions and statements

An expression has a value: 21 / 1303, len(rows), bike > 0. A statement does something: bike = 21, import csv, for ...:. A notebook cell displays the value of its last line if that line is an expression — which is why bike / workers alone on the last line shows a number, but bike = 21 shows nothing. It has no value; it has an effect.

Reading a SyntaxError

A SyntaxError is raised before a single line of your code runs — Python could not even parse it. Two things about the message matter:

  • The caret ^ points at where the parser gave up, which is often after the real mistake. An unclosed bracket on line 4 reports an error on line 5.
  • So when the flagged line looks fine, look at the line above it.
  File "your code", line 3
    for row in acs_raw
                      ^
SyntaxError: expected ':'

Given a line with a misplaced colon or bad indentation, can you locate the problem from the error message?

The procedure, in order:

  1. Read the last line of the message — it names the category (expected ':', unexpected indent, '(' was never closed).
  2. Look at the reported line. If it is obviously fine, look at the line above — unclosed brackets and missing colons report late.
  3. For indentation errors, check whether you have mixed tabs and spaces. This is invisible on screen and is why everyone settles on four spaces.

A SyntaxError means nothing ran at all. That's actually the friendly case: no half-finished state, no partly-written file. Step 11 deals with the errors that happen while running, which are messier.
