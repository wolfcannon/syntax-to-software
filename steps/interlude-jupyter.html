Jupyter notebooks

Eight steps of Python, run in a browser tab that someone else set up for you. Time to get an environment of your own — and to run what you've written against the whole county rather than eleven rows.

Why here, and not at the start

A notebook is a tool for running Python. Handed one on day one you would have had somewhere to type and nothing to type in it, and the genuinely tricky thing about notebooks — that they remember more than they show — is not a lesson you can learn before you have anything worth remembering.

You do now. build_geoid, bike_share, walk_category and summarize are a real pipeline, and the exercise boxes have got too small for them.

Getting one running

pip install jupyterlab
jupyter lab

That opens in your browser and puts you in a file list. Make a new notebook in the notebooks/ folder of this repo and call it exploration.ipynb.

If pip isn't found, try python3 -m pip install jupyterlab. If that installs into a Python you didn't expect, you have just met the problem that the second level-up solves properly with virtual environments — for now, any Jupyter that starts is fine.

Cells, and the two orders

A notebook is a list of cells. Some hold text, some hold code. Shift+Enter runs one and shows its output underneath. That much you can see.

What you can't see is that a notebook has two orders, and they are allowed to disagree:

  • Document order — top to bottom, the order a reader sees.
  • Execution order — the order you actually pressed Shift+Enter, which is whatever your afternoon happened to be.

Behind the notebook sits a kernel: a Python process that stays alive between cells and remembers every name you have ever assigned in it. The notebook file is a document. The kernel is a memory. Editing the document does not edit the memory.

The failure this causes

Your notebook works. You send it to someone. They run it top to bottom and it dies with NameError: name 'home' is not defined, because the definition only ever existed in your kernel. This is the single most common way notebook analyses turn out to be irreproducible, and the fix is a habit: Restart & Run All before you believe a result or show it to anyone.

Notice that the browser exercises never had this problem. Each one ran in a fresh namespace every time you pressed Run — which is why your code either worked or didn't, with no third state. You are giving that up in exchange for a real environment, and the habit above is what you replace it with.

Three keyboard facts

KeysDoes
Shift + EnterRun this cell, select the next
Esc then M / YTurn the cell into Markdown / back into code
Esc then 0 0Restart the kernel — i.e. empty that right-hand column

Markdown cells hold prose: what you are trying to find out, what a number means, why you threw some rows away. A notebook without them is a transcript. A notebook with them is an argument, and this project is an argument.

The level-up: run Unit 1 on the whole county

Everything you wrote in Unit 1 ran against eleven rows. Marion County has 632. The code does not need to change — that is the point of having written it as functions.

  1. Create notebooks/exploration.ipynb and put the research question in a Markdown cell at the top, in your own words.
  2. Paste in your build_geoid, bike_share, walk_category and summarize from step 8.
  3. Load the sample data first — paste data/sample_rows.py into a cell — and check summarize(acs_raw, walk_raw) gives what the browser gave you. Same code, same answer, new environment.
  4. Now swap the sample for the whole county. In a cell: 
    %run ../data/marion_full.py
  5. Run summarize again and read the numbers. How many block groups were usable? What is the mean bike share across the county? Which GEOIDs didn't join?

Then do the thing the exercise boxes couldn't: look at the distribution. Print the mean bike share within each walkability category. Four numbers, and they are the first real evidence about the research question you have ever seen.

Write in a Markdown cell what those four numbers seem to say, and what would have to be true for it to be wrong. Unit 2 spends four steps on exactly that second question.

About %run ../data/marion_full.py

That file is 632 block groups written out as Python literals, and it is a stopgap. Real data lives in data/*.csv, which is a quarter of the size and which nothing has to re-parse as source code every time. You cannot read it yet because file I/O is step 12 — so compare the two files' sizes now, and you will know why step 12 exists before you get there.

Why might a notebook that works for you fail when someone else runs it top to bottom?

Because what makes it work for you is kernel state, not the document. Three ways that happens:

  • A cell that defined something has been deleted or edited since it ran.
  • Cells were run out of order, so a later cell depends on a name that document order defines after it.
  • Something was defined in a cell you never saved, or typed into a console attached to the same kernel.

The check is mechanical: restart, run all, and see whether it survives. If it doesn't, the notebook was never really working — you just couldn't tell. Do it now, at the end of your first session, because this is exactly when a notebook has accumulated the most hidden state.
