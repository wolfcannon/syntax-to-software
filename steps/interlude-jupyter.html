Jupyter notebooks

Eight steps of Python, run in a browser tab that someone else set up for you. Time to get an environment of your own. Time to run what you have written against the whole county rather than eleven rows.

Why here, and not at the start

A notebook is a tool for running Python. On day one you would have had a place to type code and no code to type. The difficult part of notebooks is that they keep values in memory that the page does not display. You cannot learn that before you have values that you need to keep.

You do now. build_geoid, bike_share, walk_category and summarize are a real pipeline, and they are now too large for the exercise boxes.

Getting one running

pip install jupyterlab
jupyter lab

That opens in your browser and puts you in a file list. Make a new notebook in the notebooks/ folder of this repo. Call it exploration.ipynb.

If pip is not found, try python3 -m pip install jupyterlab. That may install into a Python you did not expect. If so, you have found the problem that the second level-up solves with virtual environments. For now, any Jupyter that starts is fine.

Cells, and the two orders

A notebook is a list of cells. Some hold text, some hold code. Shift+Enter runs one and shows its output underneath. That much you can see.

What you cannot see is that a notebook has two orders, and the two can differ:

  • Document order: top to bottom, the order a reader sees.
  • Execution order: the order in which you pressed Shift+Enter, which can be any order.

Each notebook is connected to a kernel: a Python process that keeps running between cells and keeps every name you have assigned in it. The notebook file is a document. The kernel holds the values in memory. Editing the document does not change the values in memory.

The failure this causes

Your notebook works. You send it to someone. They run it top to bottom and it stops with NameError: name 'home' is not defined, because the definition only ever existed in your kernel. This is the single most common way notebook analyses turn out to be irreproducible, and the fix is a habit: Restart & Run All before you believe a result or show it to anyone.

Notice that the browser exercises never had this problem. Each one ran in a fresh namespace every time you pressed Run. That is why your code either worked or did not, with no third state. You are giving that up in exchange for a real environment, and the habit above is what you replace it with.

Three keyboard facts

KeysDoes
Shift + EnterRun this cell, select the next
Esc then M / YTurn the cell into Markdown / back into code
Esc then 0 0Restart the kernel — i.e. empty that right-hand column

Markdown cells hold prose: what you are trying to find out, what a number means, why you removed some rows. A notebook without them records only what you ran. A notebook with them also gives your reasoning, and this project must give its reasoning.

The level-up: run Unit 1 on the whole county

Everything you wrote in Unit 1 ran against eleven rows. Marion County has 632. The code does not need to change. That is the point of having written it as functions.

  1. Create notebooks/exploration.ipynb. Put the research question in a Markdown cell at the top, in your own words.
  2. Paste in your build_geoid, bike_share, walk_category and summarize from step 9.
  3. Load the sample data first by pasting data/sample_rows.py into a cell. Then check that summarize(acs_raw, walk_raw) gives what the browser gave you. Same code, same answer, new environment.
  4. Now swap the sample for the whole county. In a cell: 
    %run ../data/marion_full.py
  5. Run summarize again. Read the numbers. How many block groups were usable? What is the mean bike share across the county? Which GEOIDs did not join?

Then do what was not possible in the exercise boxes: look at the distribution. Print the mean bike share within each walkability category. These four numbers are the first evidence about the research question that you have seen.

Write in a Markdown cell what you conclude from those four numbers, and what would have to be true for that conclusion to be wrong. Unit 2 uses four steps to answer that second question.

About %run ../data/marion_full.py

That file is 632 block groups written out as Python literals, and it is a temporary measure. The real data is in data/*.csv, which is a quarter of the size and which nothing has to re-parse as source code every time. You cannot read it yet because file I/O is step 13. Compare the two files' sizes now and you will know why step 13 exists before you get there.

Why might a notebook that works for you fail when someone else runs it top to bottom?

Because what makes it work for you is kernel state, not the document. Three ways that happens:

  • A cell that defined something has been deleted or edited since it ran.
  • Cells were run out of order, so a later cell depends on a name that document order defines after it.
  • Something was defined in a cell you never saved, or typed into a console attached to the same kernel.

The check is mechanical: restart, run all, and see whether it runs to the end without an error. If it does not, the notebook never worked from its document alone. You had no sign of that. Do it now, at the end of your first session, because this is exactly when a notebook has accumulated the most hidden state.
