Dictionaries

The type that turns two unrelated tables into one dataset — and the step where the project stops being exercises and starts being an analysis.

Lookup by key, not by position

A dictionary maps keys to values. Looking one up costs the same whether it holds ten entries or ten million, which is the property the rest of this step depends on.

row = {"geoid": "180973401103", "workers": 1303, "bike": 21}
row["workers"]            # 1303
row["walk_index"]         # KeyError — it isn't there
row.get("walk_index")     # None — the polite version
row.get("walk_index", 0)  # 0 — with a default of your choosing

The difference between [] and .get() is a decision about whether a missing key is a bug or a fact. For a column name you wrote yourself, missing means you typo'd it and you want the KeyError immediately. For a GEOID that may legitimately not exist in the other dataset, missing is data, and .get() lets you record it.

From positional rows to named fields

zip pairs up two sequences; dict turns pairs into a mapping. Together they convert a row you have to count your way through into one you can read:

header = acs_raw[0]
row = dict(zip(header, acs_raw[1]))
row["B08301_001E"]    # '401' — no more row[1]

This is worth doing immediately and permanently. row[8] + row[9] was fine for two steps; it is unreadable in a hundred lines and it breaks silently if the API reorders its columns.

The join

You have two tables describing the same block groups, and no relationship between them except a shared identifier. Joining means: build a lookup from one, then walk the other asking questions of it.

Composite keys

Within one county you do not strictly need a 12-character string: the tuple (tract, block_group) identifies a block group just as well, and tuples are hashable so they work as keys directly. Build the full GEOID anyway. The moment you add a second county — step 21, ticket A — a tract number alone stops being unique, and code that assumed otherwise fails in a way that looks like a data problem rather than a code problem.

Iterating a dictionary

for geoid in lookup:              # keys
for score in lookup.values():     # values
for geoid, score in lookup.items():   # both, unpacked
"180973401103" in lookup          # membership — checks keys, and is fast

Exercises

Take it further

Convert both raw tables into lists of dictionaries. Build a lookup from GEOID to walkability score. Then perform the join by hand — for each ACS row, look up its walkability score — and report three numbers: how many joined, how many ACS rows found no score, and how many walkability rows nobody asked for.

Write those three numbers down somewhere. At the level-up you will run the same code against all 632 block groups and they will change; you want the sample's numbers recorded so you can tell the difference between "more data" and "new bug".

What happens when a GEOID exists in one dataset but not the other, and how does .get() change that?

With square brackets, a missing GEOID raises KeyError and stops the loop dead on the first unmatched row. That is loud and unhelpful: you learn that one row failed, not how many.

With .get(), the lookup returns None and the loop continues. Now the absence is a value you can hold onto — count it, list it, look at a few and work out why. Roughly: square brackets for keys you believe in, .get() for keys the data is allowed to withhold.

The mistake is the third option: .get(geoid, 0). A default of zero turns "we don't know this block group's walkability" into "this block group has the lowest possible walkability", and that is now in your correlation with no trace that it was ever missing. Default to None, and decide what to do about it deliberately.
