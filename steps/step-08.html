Functions

Giving names to the three ideas you have now written out by hand a dozen times — and the point where a pile of working code turns into something that could become software.

Definition, arguments, return

def bike_share(bike, workers):
    """Fraction of workers who commute by bicycle, or None if unknowable."""
    if workers == 0:
        return None
    return bike / workers

Three things in three lines. The docstring is the first statement in the body and is what help(bike_share) prints; write it as a sentence about what comes out, not a restatement of the name. return ends the call immediately — the second return is reached only when the first was skipped. And a function that falls off the end without returning gives back None, which is a real source of confusion when you meant to return something.

Pure functions

A pure function's answer depends only on its arguments, and it changes nothing outside itself. bike_share(21, 1303) is 0.0161 today, tomorrow, and anywhere else you call it, regardless of what ran before it.

That is the property that makes the rest of this course possible. A pure function can be tested in isolation (step 18), swapped for an equivalent implementation and checked (step 9), and moved into another file without dragging context with it (step 13). Impure code — code that reads a global, or mutates a list its caller still holds — can do none of those cleanly.

The default-argument trap

Default values are evaluated once, when the def runs — not on each call. So def collect(rows=[]) shares one list across every call that omits the argument, and it accumulates. Use def collect(rows=None) and build the empty list inside. This costs people an afternoon exactly once.

Scope

Names assigned inside a function are local to it and vanish when it returns. A function can also read names from the surrounding program, which is convenient and is also how a function ends up secretly depending on a name defined somewhere else entirely — a hazard the level-up takes seriously. If a function needs a value, take it as an argument.

Take it further

You now have four functions worth keeping. Copy build_geoid(), bike_share(), walk_category() and summarize() somewhere you'll find them again — a scratch file, a note, anywhere. The very level-up has you paste them into an environment of your own.

Check them against the counts you kept in step 6: the same numbers should come out. If they don't, extracting the functions changed behaviour — and finding out which one did it is step 10.

Then take the level-up. Everything you have written so far has run against eleven rows; Marion County has 632, and your code does not need to change to handle them.

Can each function be called in isolation, with made-up arguments, and give the right answer?

That is the whole test, and it is worth applying deliberately: start from nothing, call build_geoid("01", "073", "000100", "1") with no other code around it, and see whether it works.

If it does, the function is self-contained. If it raises NameError, it was secretly reading something from the surrounding code — a header list, a lookup dict, a column index — and that dependency needs to become a parameter.

Doing this by hand is tedious, which is the entire argument for step 18. A test file is just this check, written down once and run automatically forever. You have been on the receiving end of about forty of them getting here.
