Unit 1 — Foundations · Step 7

Dictionaries

The type that lets you combine two unrelated tables into one dataset. In this step the project changes from separate exercises to an analysis.

Lookup by key, not by position

A dictionary maps keys to values. A lookup takes the same time whether it holds ten entries or ten million, which is the property the rest of this step depends on.

row = {"geoid": "180973401103", "workers": 1303, "bike": 21}
row["workers"]            # 1303
row["walk_index"]         # KeyError — it isn't there
row.get("walk_index")     # None, and no error
row.get("walk_index", 0)  # 0 — with a default of your choosing

Assigning to a key that is not there adds it. Assigning to a key that is there replaces its value.

walk_lookup = {}
walk_lookup["180973401103"] = 14.5   # adds the key "180973401103"
walk_lookup["180973401103"]          # 14.5
len(walk_lookup)                     # 1

The difference between [] and .get() is a decision about whether a missing key is a bug or a fact. For a column name you wrote yourself, missing means you mistyped it and you want the KeyError immediately. For a GEOID that may legitimately not exist in the other dataset, missing is data, and .get() lets you record it.

The two sample tables

From this step on, the exercises use two tables that are loaded for you. acs_raw holds commuting counts from the Census Bureau's American Community Survey (ACS). walk_raw holds walkability scores from the US Environmental Protection Agency (EPA).

Each table is a list of lists. The first row is a header of column names. Every value, numbers included, is text. acs_raw[6] and walk_raw[6] describe the same block group:

# acs_raw   header row       acs_raw[6]           meaning
# 0         "NAME"           "Block Group 3, ..." the block group's name
# 1         "B08301_001E"    "1303"               workers: everyone who commutes
# 2         "B08301_018E"    "21"                 bike: workers who commute by bicycle
# 3 to 5    three more columns                    not used in Unit 1
# 6         "state"          "18"                 GEOID part: state
# 7         "county"         "097"                GEOID part: county
# 8         "tract"          "340110"             GEOID part: tract
# 9         "block group"    "3"                  GEOID part: block group

# walk_raw  header row       walk_raw[6]          meaning
# 0         "STATEFP"        "18"                 GEOID part: state
# 1         "COUNTYFP"       "097"                GEOID part: county
# 2         "TRACTCE"        "340110"             GEOID part: tract
# 3         "BLKGRPCE"       "3"                  GEOID part: block group
# 4         "NatWalkInd"     "14.5"               the walkability score, 1 to 20
# 5 to 8    four ranked measures                  not used in Unit 1
# 9         "TotPop"         "2626"               total population

Joined in order, the four GEOID parts give "180973401103" in both tables. That shared GEOID is what lets you combine them.

From positional rows to named fields

zip pairs up two sequences. dict turns pairs into a mapping. Together they convert a row you read by counting positions into one you read by field name:

header = acs_raw[0]
row = dict(zip(header, acs_raw[1]))
row["B08301_001E"]    # '401': the worker count, read by name instead of row[1]

Do this conversion now, and keep it for the rest of the project. row[8] + row[9] was fine for two steps. It is hard to read in a hundred lines. If the API reorders its columns, it reads the wrong columns and reports no error.

The join

You have two tables describing the same block groups, and no relationship between them except a shared identifier. Joining means: build a lookup from one table, then walk the other and look up each row's identifier.

Composite keys

Within one county you do not strictly need a 12-character string. The tuple (tract, block_group) identifies a block group just as well, and tuples are hashable so they work as keys directly. Build the full GEOID anyway. When you add a second county, a tract number alone is no longer unique. That is step 21, ticket A. Code that assumed otherwise fails in a way that looks like a data problem rather than a code problem.

Iterating a dictionary

lookup = {"180973401103": 14.5, "180973417003": 11.833333}

for geoid in lookup:                  # keys
    print(geoid)                      # 180973401103, then 180973417003
for score in lookup.values():         # values
    print(score)                      # 14.5, then 11.833333
for geoid, score in lookup.items():   # both, unpacked
    print(geoid, score)               # 180973401103 14.5, then 180973417003 11.833333

"180973401103" in lookup              # True: membership checks keys, and is fast
"180973103083" in lookup              # False
"180973103083" not in lookup          # True: not in is the opposite of in
14.5 in lookup                        # False: values are not checked

Exercises

Take it further

Convert both raw tables into lists of dictionaries. Build a lookup from GEOID to walkability score. Then write the join yourself with a loop. For each ACS row, look up its walkability score. Report three numbers: how many joined, how many ACS rows found no score, and how many walkability rows matched no ACS row.

Write those three numbers down somewhere. At the level-up you will run the same code against all 632 block groups and they will change. You want the sample's numbers recorded so you can tell the difference between "more data" and "new bug".

What happens when a GEOID exists in one dataset but not the other, and how does .get() change that?

With square brackets, a missing GEOID raises KeyError and stops the loop on the first unmatched row. The error tells you that one row failed. It does not tell you how many rows failed.

With .get(), the lookup returns None and the loop continues. Now the absence is a value you can store. Count the missing rows, list them, examine a few and work out the cause. As a guide, use square brackets for keys that must exist. Use .get() for keys that the data can legitimately lack.

The mistake is the third option: .get(geoid, 0). A default of zero turns "we do not know this block group's walkability" into "this block group has the lowest possible walkability". That value is now in your correlation, and nothing records that it was missing. Default to None, and decide what to do about it deliberately.
