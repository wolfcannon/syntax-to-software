Unit 1 — Foundations · Step 4

Lists, tuples, and ranges

Your data arrives as a list of lists. Time to be deliberate about which sequence type means what.

Slice boundaries sit between elements

The cleanest way to stop making off-by-one errors is to stop picturing indices as labels on elements and start picturing them as the gaps between them. rows[1:4] is everything between gap 1 and gap 4 — three elements, because 4 − 1 = 3.

Two shapes you need now

You cannot do anything with a list without walking it, so here are the two pieces of syntax the rest of this page uses. Both get taught properly in step 6 — this is just enough to read what follows.

# do something once per item
for row in rows:
    print(row)

# do something only sometimes
if len(row) == 10:
    print("full row")

A colon opens the block and the indented lines under it are the block, exactly as in step 1. The name after for is yours to choose; it takes each item in turn.

List or tuple?

Both hold an ordered sequence. The difference is mutability, and the convention that has grown around it:

  • A list is a collection of things of the same kind, however many there happen to be. Rows of data. Scores. You append to it, sort it, filter it.
  • A tuple is one thing with several parts, and the number of parts is fixed by what it means. (geoid, walk_index) is a pairing, not a collection of two; there is no sensible way to append a third item to it.
scores = []                      # a list: it will grow
scores.append(("18097340110", 14.5))   # a tuple: a labelled pair
scores.sort()

pair = scores[0]
geoid, walk = pair               # unpacking: one name per part

Tuples being immutable also makes them usable as dictionary keys, which is the whole of step 5.

Sorting by something other than the value

sorted() returns a new sorted list; .sort() rearranges in place and returns None — assigning the result of .sort() to a name is a classic first-week bug. The key= argument takes a function that maps each element to the thing you actually want to sort on:

rows = acs_raw[1:]
by_workers = sorted(rows, key=lambda row: int(row[1]), reverse=True)

A lambda is a small unnamed function. Everything it does could be done by a def, which is step 8. Note the int(): sorting the raw strings would put "9" after "1303", because text sorts alphabetically.

A sort that looks right and isn't

String sorting of numeric text is one of those bugs that produces a plausible-looking answer. sorted(["9", "1303", "57"]) is ['1303', '57', '9']. If your "top 10 block groups" table ever looks strange, check that you converted before sorting.

range, and when not to use it

range(5) is 0, 1, 2, 3, 4 — half-open again. It is the right tool when you need the index itself. It is the wrong tool for walking a list: write for row in rows, not for i in range(len(rows)). When you need both, use enumerate:

for i, row in enumerate(acs_raw[1:], start=1):
    print(i, row[0])

Exercises

Take it further

In an editor above, separate acs_raw into a header and a list of data rows, and do the same for walk_raw. Build a list of (geoid, walk_index) tuples and sort it to find the most and least walkable block groups in the sample.

Then try to pair the two datasets by position — acs_rows[i] with walk_rows[i] — and print the two GEOIDs side by side. Most will differ. Positional pairing is not a join, and step 5 does it properly.

Why is (geoid, walk_index) a good tuple, but a row you intend to modify is better as a list?

Because the tuple's shape is part of its meaning. A (geoid, walk_index) pair always has exactly two parts, each with a fixed role, and unpacking it into two names is a statement about what it is. If you appended a third element it would no longer be that kind of pair.

A data row is the opposite: you want to add a computed column, replace a sentinel with None, or drop a field. Those are all mutations of a collection, and a list is the type that supports them.

The immutability has a second payoff. Because a tuple cannot change, it can be hashed, so it can be a dictionary key — (tract, block_group) is a perfectly good composite key, and that is how step 5 gets away without building a GEOID string at all.
